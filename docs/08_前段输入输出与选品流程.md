# 前段输入输出与选品流程（本轮需求澄清）

2026-10-18。依据赛题手册第3—5页及用户本轮明确要求。本文界定后续改造目标，不代表当前代码已经实现。此前0.2.0是已指定型号的检索交接实现，不是完整多轮选品；此前“预算非必填”“先提供精确型号”的规则不适用于本轮确定的选品流程。

## 一、谁使用，描述谁

直接操作者：华为门店导购、门店营销人员、内容运营。被描述对象：具体顾客或目标客群。下游消费者：图文软文、选图排版或海报合成模块。

操作者描述顾客/目标人群的画像、预算和真实使用任务，系统澄清并选品，再结合运营的发布任务整理内容依据。对话面向操作者，例如“这位顾客主要运行哪些软件”，不默认操作者本人就是购买者。运营可以描述一类客群，不强求姓名、联系方式或个人身份。

整体链路：门店/运营输入需求 → 累积并确认顾客信息 → 可选偏好澄清 → 证据驱动的候选筛选/排序 → 操作者确认产品及配置范围 → 补全营销任务 → 检索/核实产品事实及图片 → 结构化交接给下游。

## 二、输入分两层

| 层级 | 信息 | 必需时点 |
|---|---|---|
| 顾客需求 | 用户画像：个人/客群、学生/职场/创作/家庭/企业等，与选型有关的专业或工作角色 | 推荐前必须确认 |
| 顾客需求 | 预算：人民币范围、上限或明确不限预算；“5000左右”可记录近似值，需要严格筛选时确认可接受上限，不擅自扩预算 | 推荐前必须确认 |
| 顾客需求 | 实际使用场景：做什么任务、何种负载、是否移动使用；“开学季”这类营销节点不能替代学习/软件等实际使用任务 | 推荐前必须确认 |
| 顾客需求 | 偏好：尺寸/重量/屏幕/触控/颜色/存储/生态/便携/续航等，以及不接受的条件 | 可选，按相关性追问，允许跳过 |
| 顾客需求 | 必用软件、插件、外设等 | 出现明确依赖时为适配硬约束，不能当普通颜色偏好忽略 |
| 顾客需求 | 已有意向型号 | 可选；没有型号应由系统检索选品，不要求操作者先选好 |
| 顾客需求 | 购买阶段 | 可待确认；不从“咨询”自动推定已决定购买 |
| 内容任务 | 发布平台：公众号、小红书、朋友圈、海报 | 向下游交付前必须明确；不阻塞前面的选品 |
| 内容任务 | 内容目标：到店体验、私信咨询、选型教育、产品认知等 | 向下游交付前必须明确；不阻塞前面的选品 |
| 内容任务 | 营销节点、语气、强调/回避事项、门店活动要求等 | 可选；产品参数/价格/权益仍需知识库证据 |

首次输入允许一段自然语言、单条信息或结构化字段，不要求填写完整表单。明确的信息立即保存，未知项保持未知，不以演示默认值补齐。用户要求预算必填属于本项目选品规则；赛题本身要求输入产品、人群、场景、发布渠道及不足时补充，并未规定预算是所有营销任务的赛事硬性字段。

## 三、如何追问

1. 从本轮消息与已存会话槽位提取信息，只询问当前仍缺失、影响下一步决策的信息。每轮通常约2个问题；只剩1个必要问题就问1个，不凑问题，也不一次列出所有缺项。
2. 三个核心项缺失时优先补齐画像、预算、使用场景。根据已知内容调整顺序；不在需求不清时先问型号、发布平台或颜色。
3. 三项齐全后，选择最影响区分候选的约2个偏好问题，允许“一般/无偏好/跳过，先推荐”。没有会改变候选的偏好时直接检索，不机械追问。
4. 用户已经明确的软件/兼容/外设需求进入硬约束；未知适配不能用“性能强”替代证明。
5. 推荐后请操作者确认产品；必要时将产品确认与一个尚缺的内容任务问题合并。已输入平台/目标不重复问。
6. 有限追问后仍缺核心信息，不编预算、用途或型号。解释缺项，可保存当前进度；不能复制电视旧项目“超过3轮默认4000预算”等兜底规则。
7. 会话累积已确认信息，允许修改。预算/用途改变则重新筛选；产品改变则重新取证；平台改变则重新检查图量和内容策略，不能沿用不满足要求的旧就绪状态。

示例（由门店人员操作）：

- 操作者：“客户想买轻薄本。”
- 系统：“这位顾客属于哪类人群，主要用电脑做什么？预算大概多少？”（两问；第一问收集画像与实际任务，回答不完整时后续补缺）
- 操作者：“大学新生，预算6000以内。”
- 系统：“主要是写论文、上网课，还是编程/设计剪辑，有没有必用软件？对便携和屏幕尺寸有没有偏好？”
- 操作者：“文科，写论文、上网课，经常背着走，其他无要求。”
- 系统：从真实知识库检索候选，按预算与软件/场景约束筛选，再按便携等偏好排序，给出有依据的候选、理由、取舍和待核实项。
- 操作者确认某产品后，若平台和目标未知，系统再问：“准备发到哪个平台？主要希望读者到店体验、咨询配置，还是了解选型？”
- 补齐内容任务且素材证据足够后，输出下游材料包。

上例只表示对话行为，不承诺某真实型号当前符合6000元预算。若没有同SKU、适用日期/地区的价格证据，必须说明预算适配未证实；不能将该型号宣称预算内可买。

## 四、选品如何参考电视Copilot

复用思想：消息理解/路由 → 会话短期槽位 → 缺项澄清 → RAG召回 → 结构化硬约束过滤 → 场景/偏好排序 → 推荐说明与引用 → Replanner复核。

替换数据和领域规则：PC的用户画像/预算/使用任务及软件依赖代替电视尺寸/观看距离等；事实与图片来自ima，而不是把电视JSON改成PC名字。追问改为约2问/轮，不复制旧项目每次只问1题或默认预算兜底。

先筛选预算和已明确的硬约束，再按有证据的任务适配、偏好匹配排序。推荐展示少量候选（默认2—3款，有几款合格就给几款，不凑数），每款说明适合什么、依据是什么、牺牲什么、还不能确认什么。不能把标题搜索命中排序当作产品适配排序，不能把缺失值视为通过，不能把高价更接近预算直接当更优。

动态价格必须保留来源、时点、配置和适用条件。价格缺证的候选可以作为“待核价候选”，不能作为已通过预算筛选的最终推荐；超预算无合格候选时如实说明，提供调整建议并由操作者确认，不自动放宽上限。文案中不需要公开预算或价格时仍需把选品阶段的预算核实结果保留给下游。

操作者确认是具体型号还是具体SKU必须区分。如果只有型号级证据，可确认型号并标记配置未确认，跨配置参数不得混用；待确认范围影响断言时，相关生成应受限或停止。

## 五、两个不同阶段的输出

对门店/运营可见的过程中间输出：已知画像摘要、本轮约2个追问；随后为候选产品、预算核实情况、适配理由、取舍、来源与待确认条件，以及产品确认动作。这是导购/选品结果。

对下游的最终输出：既包括上述选择依据，也包括内容任务与可用素材。采用结构化接口，不把聊天记录或推荐话术直接当成完整交接。

| 图片中的字段组 | 至少交付 | 下游用途 |
|---|---|---|
| 任务上下文 | 任务/会话标识、目标人群与画像摘要、预算及核实状态、实际使用场景、营销节点（可选）、购买阶段（可待确认）、内容目标、平台、补充要求/偏好、主要问题 | 判断内容受众、切入点、表达与行动引导 |
| 产品身份 | 产品ID、标准型号、配置/版本/SKU及确认范围、确认状态；附推荐理由、候选比较摘要和预算适配证据/未知项 | 防相近型号串用，解释为何选这款 |
| 可用事实 | 事实ID、产品身份、事实内容、适用配置、限制条件、资料标题、来源定位、证据片段、资料日期（如有） | 生成卖点并逐条核验，保留条件 |
| 可用图片 | 图片ID、可预览/读取地址、对应产品身份、图片说明、来源定位、型号核实状态/核实方法；可补建议用途和插入位置、地址有效期 | 选图、预览、排版和图文一致性核验 |
| 风险与缺口 | 待确认事项、事实冲突、未找到的信息、无法支持的要求、未知预算适配/软件兼容情况、阻塞项与非阻塞限制 | 决定追问、补检索、限制生成或停止 |
| 数据状态 | 本次读取时间、来源库及来源模式、成功/需补充/冲突/不可用状态与原因、资料更新时间（若可得）、步骤记录 | 避免旧资料、失败结果或个人库结果冒充正式成功 |

补充的生成策略包括：用户痛点、内容切入点、优先卖点/事实ID、平台规则、选图建议、CTA方向、不可用说法。推荐理由是推理结果，必须关联其支持事实；不能新增未经证据支持的性能或兼容承诺。

生成就绪必须同时检查：核心需求、选品及必要确认、平台/目标、可用事实、平台要求的图片和未解决阻塞项。可以输出不完整状态包供下游展示进度，但不能把未确认产品、预算失配或资料冲突包装成可生成。前段就绪与最终可发布分别标记，后段仍负责生成后的事实/图片/合规检查。

## 六、当前代码差距与后续验收

当前0.2.0可复用的部分：ima只读调用、证据和图片提取、平台规则、材料协议与失败状态。需要改造的部分：多轮会话状态、必需三槽位、预算表示与证据核实、可选偏好约2问/轮、全库候选筛选排序、推荐后产品确认、内容任务补全，以及将新信息明确纳入交接协议。旧CLI默认补齐的表单不能继续作为多轮导购测试入口。

验收至少包括：只给人群/只给预算/只给一句需求均能正确补问；已说过的信息不重复问；可选偏好能跳过；明确软件依赖不忽略；缺价格不称预算满足；无合格候选不凑数；推荐后换预算重筛；确认产品再补平台目标；最终完整交付上表六组信息；个人库仍明确标为个人库联调。
