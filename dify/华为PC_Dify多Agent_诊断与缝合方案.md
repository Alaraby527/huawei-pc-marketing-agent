## 1. 赛题硬性要求对照（评分锚点）

复赛 100 分分布：业务场景理解 20 / **产品事实准确性 20** / 图文生成与图片引用 15 / 平台适配 15 / 自研 Agent 与提示词 15 / 功能完成度 10 / 合规与安全 5。

两条一票否决：**图片非来自 ima 或型号不符 → 图片引用项 0 分；虚构价格/补贴/销量/奖项/评价 → 准确性和合规性 0 分。**
不进复赛情形之一：**"完全由 ima 直接生成最终软文，自研系统仅作转发"** —— Dify 工作流本身就是"自研 Agent"的证明，这是把链路搭在 Dify 上的合规性依据。

统一输出格式（现场检查项）：**一、场景判断 → 二、知识库依据 → 三、图文软文 → 四、核验结果**。

当前 Dify 现状与要求的差距：
- 标准流程 9 步（场景解析→平台策略→ima 检索→事实提取→图文编排→软文生成→事实与图片核验→合规检查→导出）：Dify 目前只覆盖"场景解析 + 检索 + 事实提取 + 选品"，**后 5 步缺失**。
- ima 调用：Dify 无 ima 连接器。产品事实走 Dify 知识库（官方 v7 ZIP 导出）可以支撑"事实准确性"，但**图片引用 15 分必须走 ima**——建议把代码侧 `ima.py` 包成 HTTP 服务注册为 Dify 自定义工具（见 §5.3）。

### 2.2 问题清单

**P0-1 切片严重碎片化（单行切片）。** 实测 Fold 文档第 175–180 段全部是单行 bullet：`- 支持 P3 广色域。`（12 词）、`表达边界**`（6 词，是 `- **像素与表达边界**` 被切开的残片）、`- 1600 nits 是 HDR 内容下局部峰值…`（35 词）。推测按 `\n` 逐行切片。一个 37,826 字的型号文档被切成上千个微碎片，导致：
- 语义检索命中的是孤立行，字段名和值分离（"屏幕"一节被拆成十几段）；
- 你们的 `⑦证据包组装` 代码节点被迫写了 2 万字符去从碎片里拼 matrix/colon/tree 三种形态——这是在代码里硬扛切片错误，属于**用下游复杂性掩盖上游问题**；
- top_k=60 也正是碎片化的代偿（单段信息量太小只能多捞）。

**P0-2 零元数据 → 分层检索设计没有落地。** 你规划里"商品参数层精确匹配、活动层时间标签自动过期、按型号多维度检索"全部依赖 metadata 过滤，但现在 `doc_metadata=[]`：检索无法按 `model_name` 过滤（跨型号污染 = 复赛"易混淆型号"现场检查直接踩雷），无法按 `snapshot_date` 过期历史价格。目前唯一防串型的手段是 LLM 型号规范化 + 代码比对，这个设计不错但属于"事后过滤"，检索阶段捞 60 段里可能根本没有目标型号的段落。

**P0-3 8ef 应用「产品基础参数检索」节点挂在空库上。** dataset_id `02ebe307` 是旧的「01-商品参数库」（0 文档、2 个月前建的测试库），不是新的 `425b7e38`。参数查询分支检索永远返回空。

**P1-4 检索方式单一。** 01 参数库全是 semantic_search，但型号名（MateBook 14 酷睿 Ultra vs 鸿蒙版）是精确词，语义向量对这种区分度弱，应开 hybrid（关键词+语义加权）。

**P1-5 02/03/04/06/07/08 六个库建了没接。** 05 库 top_k=20 也过大；02 价格快照没有任何"当期价格维护格式"（代码侧有 14 条 blockers 的 `verified-price` 记录格式，Dify 侧没有对应物）。

**P2-6 05 库单文档过大。** 「客户与行业场景｜上/下篇」各 18 万字，检索噪声大，应按人群/场景拆成独立小文档（每篇一个场景卡）。

### 2.3 修复方案（分层差异化切片 + 元数据 + 检索配置）

统一动作：每库开启**元数据字段**（知识库 → Metadata → Add Field），文档级打标；重切片用「重新处理文档」或重新上传（源文件就是 v7 ZIP 合并脚本产物，改脚本的分段符即可重新生成）。

| 库 | 切片策略 | 分段设置 | 元数据字段 | 检索配置 |
|---|---|---|---|---|
| 01_商品基础参数（慢更新·精确匹配） | **父子分段**（child=规格小节，parent=整型号文档）或 General | 分段标识符 `\n\n## `，最大 1000 token，重叠 100 | `model_name`(必填、单选), `category`(笔记本/显示器/配件…), `source_path`, `captured_at`(日期) | **hybrid**（关键词 0.7/语义 0.3 或 weighted），top_k **12**，score ≥0.35，qwen3-rerank 开 |
| 05_客户场景与型号话术（中频·语义） | 父子分段 | child 400 token，`\n\n## ` | `model_name`, `audience`(学生/职场/创作/家庭/企业), `scenario` | semantic，top_k **6**，rerank 开 |
| 02_历史价格快照（高频·短切片+过期） | **Q&A 模式**或 General 短片 | 300 token | `snapshot_date`(必填), `scope`=historical_only, `model_name` | 检索节点开 metadata 过滤：`snapshot_date` ≥ 当月；**文案链路默认不接此库**，只有价格核验环节读 |
| 03_受限政策模板 | General | 500 token | `policy_type`, `restricted_scope` | top_k 3，作为合规环节输入 |
| 04_履约与售后支持 | General | 600 token，`\n\n## ` | `region`(全国/分省), `service_type` | top_k 4；地域问题按 `region` 过滤 |
| 06_营销素材与表达参考 | Q&A / 父子 | 400 token | `platform`, `audience`, `style` | top_k 4；写手环节按 `platform` 过滤 |
| 07_竞品资料 | General | 600 token | `brand`, `model_name` | top_k 3；**只供对比环节引用库内数据，禁止流入卖点** |
| 08_培训与建库治理 | General | 800 token | — | 不接入运行链路，团队 SOP 用 |

> 说明：Dify 的知识检索节点支持「元数据条件过滤」（Metadata Filtering），把 `model_name` 设为必填后，工作流里 `⑤型号规范化` 输出的标准型号可直接作为过滤值传入 01 库检索节点——这就把"型号身份过滤"从 LLM 事后比对前移到了检索层，是解决"相近型号参数错配"的最硬手段。

**更新 SOP（对应你规划的六步，落到 Dify 操作）**：
1. 新品上架 → 用合并脚本生成该型号 md（保留来源信封）；
2. 参数录入 → 05 话术卡、06 素材同步补；
3. 标签校验 → 上传时必填 `model_name` 等元数据，缺失即拒绝（Dify 必填字段开关）；
4. 切片生成 → 按上表分段配置，入库后抽查 10 段看字段完整性；
5. 离线评测 → 召回测试集（每型号 5 条 query：型号全名/简称/系列名/配置问法/易混淆型号），在知识库「命中测试」里跑，要求目标型号文档 top3 命中率 100%；
6. 灰度上线 → 先在工作流调试页跑 10 组任务再发布。

## 3. 多 Agent 协作诊断

### 3.1 主工作流「华为PC·商品推荐环节（证据约束选品）」（18 节点，质量最高的一个）

```
开始 → ①需求解析(LLM, JSON) → ②结构化解析(code) → ③完整性闸(if)
  ├─缺参→ ④缺参追问(LLM) → ④a渲染(code) → 追问回复
  └─完整→ ⑤a型号清单(code, 硬编码KB文档名) → ⑤型号规范化(LLM: verified/ambiguous/not_found)
        → ⑤b检索式构造(code) → ⑥事实卡检索(01库, top_k=60)
        → ⑦证据包组装(code 2万字符) → ⑧证据闸(if: enough/partial/false)
            ├─false→ ⑩a资料不足(code) → 资料不足回复
            └─ok→ ⑨选品判定(LLM, 只引fact_id) → ⑨a选品结论(code) → 选品回复
```

**做得好的（保持）**：
- 型号身份白名单（⑤a code 给 LLM 唯一合法取值清单）——这正是代码库 `model_from_document` 的 Dify 化，方向对；
- 证据闸三档 + "资料不足就明说不推荐"，忠实继承了代码侧"没有证据就停下来"的原则；
- 选品判定提示词"reasons 里 fact_id 必须真实存在、不得输出证据包之外的型号/价格"——事实白名单思想的雏形；
- 每个代码节点都处理了 deepseek `<think>` 未闭合标签的问题（防御性解析很扎实）。

**问题**：
- **P0-1 澄清循环无状态。** `conversation_variables: []`。用户回答完 ④ 的追问后，下一轮重新走 ①，槽位是否延续完全靠 ①LLM 的 memory 回忆，`②` 的 missing 重算没有跨轮槽位合并逻辑；也没有 clarify_count 上限与"3 次后按默认画像强制出稿"的兜底。
- **P0-2 覆盖面只有选品。** 按应用自述"文案、合规、配图由后续环节负责"——但 Dify 上没有后续环节的应用。
- **P1-3 ⑨选品判定 的 user prompt 是 `{{#sys.query#}}` 原句**而不是 ② 的槽位 JSON，人群/场景要靠模型自己再读一遍原话。
- **P1-4 ⑦证据包组装 2 万字符代码在替切片背锅**（§2.2 P0-1），重切片后可砍掉 2/3。
- **P1-5 无改稿分支**："再来一版更活泼的"这类编辑指令会走完整链路重新选品。
- **P2-6 ⑤a 型号清单硬编码**在 code 里，新增型号要改节点代码——改成环境变量或从 08 库读。

### 3.2 门店宣发上游Agent - 产品精准检索（8ef，京言式路由）

主控路由（问题分类器 5 类）→ exact_lookup 走检索→型号消歧→参数取证→复核重规划→合规审查 → 汇聚输出。

**问题**：
- P0 「产品基础参数检索」挂空库（§2.2 P0-3）；「知识检索 5」挂的却是 05 话术库（给"参数取证"喂话术，语义错位）；
- P1 与主工作流功能重叠（都在做"型号规范化+参数检索"），双线维护会漂移——**建议废弃或降级为实验场，收敛到主工作流**；
- 京言 DSL 的老问题也带过来了：无槽位变量、合规是单遍 LLM 无重试降级（代码版有 MAX_RETRY=2 + 安全模板）。

### 3.3 66d（Agent 节点版）与 多轮需求拆解/需求拆解/每日内容策划

早期原型，价值不大，建议归档，避免评审时点开发现半成品。

### 3.4 与两个代码项目的差距（京言评测报告的教训直接适用）

京言 Dify 版 V1.0 幻觉 4 次的根因 = 检索碎片 + LLM 自由发挥 + 无白名单校验。你们主工作流已经补了白名单校验，但**后端文案环节如果照现在这样直接 LLM 生成，会重蹈覆辙**。V1.0→V1.1 92% 的修复手段（"所有参数必须来自知识库，禁止编造""未命中就说暂未收录"）请直接写进写手提示词。

## 4. 缝合方案：目标工作流蓝图

> ⚠️ 2026-10-24 更新：本环节负责人确认**只负责选品**（平台策略/文案/合规/图片引用由队友负责），且要求升级为「主控 Agent + 多个子 Agent」架构。本章的全链路设计保留给队友参考；选品环节的最终设计见 **《选品环节_多Agent重构蓝图.md》**（主控 ChiefPicker + 5 个子 Agent，各自独立 Workflow 应用发布为工具）。§2 知识库修复方案不变，仍是全部环节的地基。

**一个 Chatflow 打通全链路**（在主工作流基础上扩展，节点从 18 → 26 个），名字建议：`华为PC·门店宣发Agent（全链路）`。

### 4.1 总拓扑

```
开始(开场白+建议问题做成傻瓜式模板)
→ ① 需求解析 LLM 【改造：槽位扩为 model_raw/audience/scenario/platform/campaign/tone/edit_intent】
→ ①b 槽位合并 code 【新增：与会话变量 slots 合并，空值不覆盖；edit_intent=改稿→走 ⑮】
→ ② 完整性闸 if 【改造：必填= audience+platform（型号不问！）；clarify_count<3】
    ├─缺 → ③ 澄清 LLM（选项式）→ 回复（clarify_count+1）
    └─齐 → ⑤ 型号规范化（保留现有⑤a/⑤，清单改环境变量）
        ├─ ambiguous/not_found → 澄清分支（列候选型号）
        └─ verified → ⑥ 三路并行检索【改造】
             R1 01_商品基础参数：query=型号名，metadata 过滤 model_name=<标准型号>，top_k 12
             R2 05_客户场景与型号话术：query=型号+人群+场景，top_k 6
             R3 06_营销素材与表达参考：query=平台+人群，metadata 过滤 platform，top_k 4
        → ⑦ 证据包组装 code 【瘦身：重切片后只做 fact 编号+型号一致性校验+coverage】
        → ⑧ 证据闸（保留三档；false→资料不足回复）
        → ⑨ 场景×平台策略 code 【新增：路由表注入，见 4.3】
        → ⑩ 写手 LLM 【新增：事实白名单提示词，四段式统一输出，temp 0.4】
        → ⑪ 合规扫描 code 【新增：正则红线，见 4.4】
        → ⑫ 合规闸 if：pass→⑬ / fail→修正重写（循环≤2）→仍fail→安全模板+转人工话术
        → ⑬ 独立审校 LLM 【新增：verdict 六值，只见成稿+事实包】
        → ⑭ 渲染导出 code（四段式报告+待确认清单）→ 回复
→ ⑮ 编辑分支 LLM 【新增：对会话变量里的 draft 做局部 patch，只改用户指定处】
```

**会话变量（conversation_variables，新增 4 个）**：
```json
[
 {"name":"slots","value":"{}"},            // 槽位累积：audience/platform/scenario/campaign/model_name...
 {"name":"clarify_count","value":0},        // 澄清轮次，上限3
 {"name":"evidence_pack","value":"{}"},     // 本轮证据包（fact_id 索引）
 {"name":"draft","value":"{}"}              // 当前成稿，供改稿分支
]
```

### 4.2 各节点核心配置（可直接粘贴）

**① 需求解析 LLM（system，替换现有版）**——融合代码侧 guided 四件事 + "不问型号"铁律：

```
你是华为PC门店宣发任务的需求解析器。把用户输入拆成结构化字段，不做任何创作。

## 提取字段
model_raw（用户点名的型号，没提填null，禁止从"轻薄本"推型号）
audience（目标人群：大学新生/家长/职场商务/创作者/家庭换新/企业采购/到店顾客…）
platform（发布平台：小红书/公众号/朋友圈/门店海报，没提填null，不要默认）
scenario（使用场景/业务场景：开学季/差旅办公/视频剪辑/家庭换新/新品首发/节日送礼…）
campaign（要打的活动节点：开学季/618/双11/门店活动…，用户说"没有活动"则填"none"）
tone（语气偏好，null=不限）
edit_intent（用户在改上一次的稿子吗？改=edit，否则 new）

## 规则
1. 只抽取明确说过或无歧义可推出的内容；宁缺勿猜。
2. 不要问型号：用户通常不知道型号，型号由下游从知识库匹配；用户点名了型号才填 model_raw。
```

**⑪ 合规扫描 code（新增）**——`compliance.py` + `content_policy.py` 的正则族，纯函数直接搬：

```python
import re
ABSOLUTE = ["全网最低","全网第一","最好","最强","天花板","吊打","闭眼冲","闭眼入","秒杀所有","绝对","永久免费","买它就对了","无脑冲","碾压","完美无缺","第一","100%","顶级"]
FAKE_EXP = [r"亲测", r"实测(续航|成绩|性能|跑分|数据|结果)", r"用了\d+[天周月]", r"我连续用了", r"体验了一个月"]
UNVERIFIED_BIZ = [r"\d+元", "国补", "补贴", "优惠", "折扣", "赠品", "秒杀", "限时", "库存紧张", r"仅剩\d+件", "销量第一", r"好评率\d+%", "获奖", "认证第一"]
DEROGATORY = [r"友商.{0,8}(垫底|最差|不如|吊打)", r"别家.{0,6}(垃圾|不行)"]
PLACEHOLDER = [r"\{\{.*?\}\}", "TODO", "TBD", "待补", "待定", r"X元", r"X折", "undefined", "NaN"]

def main(text: str, facts_json: str) -> dict:
    import json
    errors, warnings = [], []
    for w in ABSOLUTE:
        if w in text: errors.append(f"绝对化用语: {w}")
    for p in FAKE_EXP + UNVERIFIED_BIZ + DEROGATORY:
        if re.search(p, text): errors.append(f"违规表述: {p}")
    for p in PLACEHOLDER:
        if re.search(p, text): errors.append(f"未解决占位符: {p}")
    # 数字溯源：文案数字 ⊆ 事实数字集合
    facts = json.loads(facts_json or "{}")
    fact_nums = set(re.findall(r"\d+(?:\.\d+)?", json.dumps(facts, ensure_ascii=False)))
    text_nums = set(re.findall(r"\d+(?:\.\d+)?", text))
    leaked = text_nums - fact_nums
    if leaked: errors.append(f"事实未支持的数字: {sorted(leaked)}")
    if len(re.findall(r"#\d+元|价格", text)) and not facts.get("price_verified"):
        warnings.append("涉及价格但无当日核价记录，需删除或标注以门店为准")
    passed = not errors
    return {"passed": passed, "errors": errors, "warnings": warnings,
            "output": text if passed else "BLOCKED: " + "; ".join(errors)}
```
